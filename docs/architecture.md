# Architecture

Silicon Canvas 有两个用户入口，复用同一套 Python 核心。

| 层 | Web | MCP |
| --- | --- | --- |
| 输入 | 一个主输入框中的设计与视觉要求、自然反馈，以及可选的自定义设置 | 宿主 Agent 描述、反馈或已有结构规格 |
| 语义整理 | 浏览器直接调用用户配置的模型服务 | 宿主 Agent 整理规格；可选本机模型接口 |
| 编译 | Pyodide Web Worker 内的 Python 核心 | 本机 Python 核心 |
| 字体与规则 | 随静态发布物提供 | 随 Python 包提供 |
| 输出 | 提示词、必要配套文件提示、绘图包与项目文件下载 | MCP 工具结果、资源与本机绘图包 |

`engine.prepare_request` 准备规格要求，`engine.finish_request` 校验模型回复并编译，`engine.compile_manual` 编译已形成的规格。模型传输与编译分离，宿主 Agent、DeepSeek 和其他兼容服务均可提供同一种源规格。

## 共享设计策略

工程视图使用 `diagram_design` 等规划记录：主要阅读问题、可见与局部展开的源成员、真实归属、对象角色、分支与汇合、文字负担和可行的重组方向。它依据实际底稿统计图内信息，包含同一硬件的解释性展开，不能用宏观方框数量代替真实复杂度。算法与渲染采用各自的计算或画面计划；自然描述仍是默认输入，这些内部决策不变成新的必填分类表。

工程表达可以组合不同语法。层级架构与源结构支持的重复阵列采用版面候选；数学数据流采用张量、算子与依赖；状态图保留条件和自环；精确采样数据采用共同时间轴；明确逻辑网格保留现有邻接与外围附着；有返回控制的短路径使用独立收发端口。系统不会从一个 DAG 推导执行周期，也不会把用于绘图的网格嵌入称为实测 floorplan。

设计依据见 [视觉设计研究](visual-design-research.md)，原创挑战集与验证范围见 [通用设计基准](design-benchmark.md)。`diagram-design.json`、`semantic-plan.json` 与已有算法/渲染计划一起导出，Web、Python 与 MCP 使用同一份规划与源事实。

## 源事实、用途与表达

| 记录 | 职责 | 不承担的含义 |
| --- | --- | --- |
| 完整源事实 `spec` | 模块、归属、显式数量、条件、连接、出处与技术假设 | 不自动推断实际芯片面积、裸片划分或封装几何 |
| 内容用途 `scene_profile` | 读者问题、整体或局部范围、数据过程、详略与配套视图 | 不固定三维、平面、材质或品牌 |
| 表现形式与艺术方向 `representation_profile` / `render_brief` | 商业渲染、空间系统示意或工程图；主体尺度、解释方式、镜头、材质、光照与重点 | 不把视觉选择升级为技术事实 |

`scene`、`representation` 与独立色板 `style` 可以组合。自然输入保存在画面方案中，用户明确的视觉方向优先于默认镜头和材质。新准备与生成流程默认两项自动选择，未提供新表现形式字段的旧规格直接编译继续使用工程图策略。

## 两条编译路径

工程表达按内容采用合适语法。硬件结构由 `reading_plan` 确定阅读问题与显示范围，经过布局候选、结构底稿与提示词编译；状态、时序保留各自的条件和时间含义。数学数据流使用张量、算子与依赖计划，不强加硬件底稿。复杂设计可以生成主图和技术附图，完整源规格与显示投影分别保存。

产品渲染与系统示意分两层决定画面。`render_strategy` 先判断主角是什么、处于什么尺度：一个封装、一块板卡、整台设备，还是多个节点组成的系统。内部提到的芯片或逻辑模块不能替代整个主体，也不能因为模块多就被画成多个裸片。

`render_brief` 的 `RENDER3` 契约再把主体与阅读任务组织成完整画面：选定外观主视觉、外围上下文、内部功能解释或组装视图，并给出匹配尺度的镜头、材质、光照与标注。机柜、板卡和封装不再共用同一套固定拍摄方式。可见对象与关系仍映射到源事实，艺术方向不授权增加主要功能器件、改变归属或声称真实制造布局。具体边界见 [表达方式与用途](scenes.md) 与 [渲染策略](render-strategy.md)。

渲染默认一次生成完整画面。明确要求保留已批准主体或分步精修时，编译资料可以包含以真实成图为目标的编辑步骤，交给 Agent 或图片工具执行；当前网页不提供分步图片编辑器。自然反馈重新进入编译流程，按结构锁与既有设置保留相应事实和表现合同。

`render_guide` 生成可选取景参考，只说明主体范围与留白。它不约束实际表面、透视、材质或照明；产品渲染可以只用编译提示词完成 Image Gen 调用。工程图的 `layout-guide.png` 则承担精确结构约束，两种参考不能混用。

`bundle` 把逐图提示词、`render-brief.json` 或布局记录、图注、源规格与参考一起导出。`quality_review` 按表现形式准备实际图片审查，初始状态保持 `not_reviewed`。

## 共享与边界

### 一致的视觉规则

`visual_style` 从 catalog 读取唯一的配色定义，供提示词和程序生成的结构参考共同使用。当前结构化设置优先于旧提示词中的颜色文本；旧保存结果仍有兼容读取路径。单色风格连缓存中的路径颜色也转换为灰度，避免参考图和文字要求互相冲突。

`visual_language` 将颜色映射到当前图形的含义：工程图区分计算、存储与控制，算法图区分张量、算子与状态。共用的文字层级、浅色标题、轻边界和留白规则随 `visual_contract` 一起返回给 Web 与 MCP，并写入导出包。用户在描述或补充要求中表达的外观意图保留在实际生成提示词中，优先于预设；它不增加当前视图之外的技术事实。

渲染分支先解析 `flat_2d / orthographic / dimensional`，再写入有效的相机、材质、光照与构图指令。二维说明图不会继承三维产品默认要求；俯视或正交产品图仍可保留材料深度。识别是有限的自然语言规则，原始要求仍保留供模型理解与成图复核。

参考库匹配依据最终可见的对象和连接，不用折叠的内部细节驱动概览风格。已匹配且确有结构依据的表达机制最多选两条进入提示词，例如保持独立操作数入口清晰或让既有对等单元保持一致；不会从参考图导入厂商品牌、拓扑或额外硬件。

这套规则借鉴了[按语义角色使用颜色](https://designsystem.harvardsites.harvard.edu/color-roles)的设计方法，并结合本地论文与商业架构图的参考标注。规则一致性不等于实际成图质量：实际图片仍需观察层级、文字、连线与内容，`visual_contract` 不产生自动审美评分。

当前网页是简洁的“网页演示版”：描述内容后生成提示词，用“自定义”覆盖自动选项，生成后可复制提示词、下载绘图包或保存项目 JSON；多视图结果提供一个视图选择器。图片生成在 ChatGPT 等工具中进行，网页不展示结构底稿或直接生成最终图片。项目 JSON 是保存与交接资料，当前页面没有项目或规格导入入口。

“再调整一下”提交自然反馈，沿用当前结果已保存的设置；“保留当前模块与连接”默认开启。改变自定义选项用于下一次主输入生成，不会立即重新编译现有结果。完整的 Agent 流程由 [MCP 入口](../web/agent.html) 说明，首页 [精选作品](../web/index.html#showcaseTitle) 展示实际输出。

浏览器执行打包后的同一份 Python 核心，不另写 JavaScript 画面规则。API 请求留在页面 JavaScript；Worker 仅处理没有 Key 的描述、规格和编译数据。MCP 直接调用本机核心，不依赖网页或旧 HTTP 服务。

程序生成的参考图用于传达结构或取景意图。最终产品渲染、系统插画和工程位图均由 Image Gen 生成。源事实完整、布局预检、外观假设与实际图片审核分别记录，不能相互替代。

工程复杂度超出版面能力时可能出现附图或 fallback，应查看具体预检与限制。渲染预检只能检查方案与事实记录的职责边界，不能证明照明、材质、物体形态或最终标签已经正确。
