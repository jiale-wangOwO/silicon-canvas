# 表达方式与用途

Silicon Canvas 先判断画面要回答什么，再选择显示内容和视觉语言。质感、透视与光照服务于表达；产品外观、功能分区、系统上下文和精确工程关系都有各自的使用场景。

## 表达形式

| 形式 | 主要画面语言 | 适合目标 |
| --- | --- | --- |
| 商业渲染 `product_render` | 产品主体与受控材质、光照；按目标组合功能说明、外围对象、关键关系或文案留白 | 产品介绍、BP 方案页、能力演示、发布会主视觉 |
| 系统示意 `system_illustration` | 逻辑功能区、空间层次、资源归属、外围上下文与主路径；可半写实、等距或平面 | 系统演示、功能概览、技术产品介绍、原理讲解 |
| 工程图 `diagram` | 模块、分区、标签、端点与明确的技术连接；精确结构底稿约束几何 | 架构文档、论文机制、微架构、数据流与设计评审 |

三种形式提供不同的编译策略。具体镜头、材质、信息量与构图仍按描述决定。商业渲染可以讲系统方案；系统示意可以带产品质感；封面主视觉则可以保留少量文字，突出外观与气氛。

Web 默认 `representation: "auto"`。系统结合用途与内容决定形式及解释范围。“BP”或“商业”本身并不意味着只画封装外观；要介绍计算、存储与接口协作时，应显示相应功能与关系。明确请求封面、无字主视觉或轮廓展示时，才优先突出外观。纯平面框图、数据流、状态机和时序通常使用工程图。需要覆盖自动判断时，展开主输入框下方的“自定义”，从“表现形式”等下拉选项中选择；具体画面要求与设计内容写在同一个描述框中。

## 一张图要回答的问题

渲染编译内部使用 `render_brief.explanation_plan` 规划阅读目标。它不是另一套需要用户手动选择的类型列表：

| 内部模式 | 画面要讲什么 | 显示内容 |
| --- | --- | --- |
| `hero` | 产品的整体形象是什么 | 产品主体、轮廓、材质、气氛与必要品牌文字 |
| `annotated_context` | 芯片在完整系统中负责什么 | 产品主体、外围资源、功能职责与主要接口 |
| `functional_cutaway` | 内部功能怎样组织和协作 | 逻辑功能区、共享资源、片上互联与关键外部连接 |
| `assembly` | 系统由什么组成，各部分怎样关联 | 来源明确的器件或层次、组成关系与连接 |

`reading_question` 记录阅读问题，`visible_summary` 记录本图显示什么。它们保留在编译结果、MCP 资源和绘图包中；当前网页以提示词和必要配套文件提示作为主要交接，不提供单独的阅读计划面板。具体可视对象、功能分区和关系由源规格投影，完整模块与连接仍保存在源规格中。

新版渲染先确定“主角是什么”，再决定“怎样解释”。`render_strategy` 根据原始主体、器件角色与归属区分封装、板卡、服务器、机柜或多个节点组成的系统；`RENDER3` 再结合上面的解释模式安排镜头、材质、层级、留白和标注。系统节点保持独立设备身份，逻辑功能区不自动变成物理芯粒。尺度与阅读任务会改变画面组织，风格不只是换颜色。

解释性渲染可以让芯片主体承载逻辑功能分区。应有明确层级、有限强调色、清楚的主路径与易读标签；透视强度、微纹理、发光与材质细节要服从使用尺寸和信息清晰度。逻辑分区表示功能组织，不能从其面积与位置推定实际 die 布局。器件外观和装配形态缺失时以概念表现记录，不从逻辑模块数量推定 die 数量、存储封装或物理层数。

## 用途是另一层决策

| 用途 | 读者首先要理解 | 信息取舍 |
| --- | --- | --- |
| 整体概念 `concept` | 产品或方案是什么、在完整系统中做什么 | 完整主体与主要能力，内部实现可留给技术附图 |
| 系统组织 `system` | 子系统怎样组织、资源属于谁、接口在哪里 | 功能层级、共享资源与主要接口 |
| 工作过程 `flow` | 数据或任务从哪里来、怎样处理、如何返回 | 阶段、分支、汇合与返回；依据真实设计关系 |
| 实现细节 `detail` | 具体资源、端点与条件怎样实现设计 | 聚焦可读的真实技术范围，保留必要数据与控制关系 |

用途 `scene`、形式 `representation`、色板 `style` 可以分别设置。BP 方案页可以选带外围关系的产品渲染，也可以选功能分区概览。系统原理页可以选解释性渲染，也可以选精确框图。在描述中说明要讲的内容和期望画面即可，不需要另填补充要求或标签表单。

Web 把形式、用途、配色、详略、画幅和展示视角收进默认关闭的“自定义”。用户无需先替系统做分类，直接描述内容即可开始；“恢复自动”清除这些手动选择。新请求的图中文字使用英文，输入仍可以是中文。

## 生成与编辑

算法数据流根据张量、算子与实际依赖自动组织画面：保留独立输入、真正的汇合点、旁路、归约、状态递推及给定的数据驻留。算法主图直接使用提示词生图，构图方案和源关系随包导出。具体方法见 [算法数据流](algorithm-dataflow.md)。

解释性渲染默认一次生成完整画面。只有用户明确要求分步生成、希望保留已批准主体等情况，编译资料才可能包含编辑步骤；这些步骤供 Agent 或图片生成工具执行，当前 Web 不显示步骤标签或分步编辑界面。

编辑步骤以实际成图为 Image Gen 编辑目标。可选构图参考表达位置与范围，不替代待编辑的真实图片。工程图则用精确结构底稿约束模块归属、标签和连接方向。最终成图始终来自 Image Gen；编译底稿与参考本身不是最终图片。

源规格、图注与审查材料保留技术含义。产品的概念外观、逻辑分区与工程假设分别记录。未提供的工艺、封装尺寸、性能、容量、供应商标识与实际布局，不应从渲染中推定。技术附图可展开具体模块与连接，供核对主图取舍。

## 在 Web 与 MCP 中使用

网页演示版的“试个例子”会填入一段 GPU 请求，描述任务分发、计算簇、共享 L2 与显存路径，同时恢复自动选项。用户可以直接修改这段描述，不需要先选择某个场景模板。

生成后，页面提供原始提示词、复制按钮和“下载绘图包”；多个视图可在结果区切换。需要配套图片的工程视图会提示一起使用绘图包中的文件；若必要参考未能生成，页面会明确提示。产品渲染的构图参考是可选的，数学算法图可以只用提示词。最终图片仍由外部 Image Gen 生成。

“再调整一下”接受自然反馈，沿用当前结果已保存的设置；“保留当前模块与连接”默认开启。改变“自定义”只影响下一次主输入生成，不会自动套用到现有结果。更多导出选项可保存提示词文本和项目 JSON；项目文件不包含 API Key，当前网页没有项目或规格导入入口。

MCP 输入接受 `representation: "auto"` 或三种形式 ID，`scene` 接受自动或四种用途 ID。例如：

```json
{
  "representation": "auto",
  "scene": "concept",
  "notes": "为 BP 解释芯片与片外 DRAM、主机和传感器的关系；浅灰背景，轻透视，功能说明与主要接口清楚可读"
}
```

MCP 的默认流程是 `silicon_prepare` → 宿主整理完整源规格 → `silicon_compile` → 宿主调用 Image Gen 并查看成图；语义理解使用宿主现有模型。详细接入见 [插件与 MCP 接入指南](mcp.md)。

返回的 `settings.representation` 是请求形式，`settings.resolved_representation` 和 `representation_profile` 记录实际选择，`scene_profile` 记录内容用途。Agent 可以基于已有源规格重新编译，不直接信任旧文件缓存的选择与几何。

已有规格直接编译且没有 `representation` 字段时保留工程图兼容行为；新准备与生成请求默认自动匹配。这是共享核心与 MCP 的兼容合同，不表示网页提供导入或本地套用按钮。

实际输出可查看 [首页精选作品](../web/index.html#showcaseTitle)。更完整的长期依据见 [整体系统设计](system-design.md)、[渲染策略](render-strategy.md) 与 [视觉设计研究](visual-design-research.md)。精选样图与编译参考都不能代替每次实际成图后的核对。
