# 从输入到成图的整体设计

Silicon Canvas 的目标是把不同的设计说明转换成有结构、可理解、适合实际用途的 Image Gen 绘图方案。一次修改只有改善同类输入的处理能力、保留其他表达任务的能力，才算产品改进。某张样图变好、路线变短或回归测试通过，都不能独立证明这一目标已经达到。

## 一条共享流程

Web 和 MCP 使用同一条流程：

`自然描述与反馈 → 完整源规格 → 用途与表现形式 → 可见范围与阅读方式 → 图像提示词及相应参考 → 实际成图审查`

自然描述仍是默认输入。用户无需先懂图的分类，也不必填写模块清单、布局坐标或审美问卷。信息较少时，自动补全可以提出完整、可修改的通用方案；详细输入与明确排除项则约束补全范围。技术假设留在源规格与图注中，不能伪装成给定事实。

网页演示版围绕一个主输入框组织：设计内容、视觉要求与必须保留的文字都写在这里，图中文字使用英文。形式、用途、配色、详略、画幅和展示视角默认自动安排，必要时才展开“自定义”。结果以原始提示词、必要配套文件提示和绘图包交接给图片生成工具；网页不直接生图，也不显示独立的源规格编辑器、结构参考面板或分步图片编辑器。

Agent 是完整协作入口。宿主调用 `silicon_prepare` 获取规格要求，用自己的模型整理源规格，再调用 `silicon_compile` 并按返回合同使用 Image Gen。图片生成与实际看图由宿主完成，默认流程不需要额外语义 API Key。两种入口复用编译策略，但自然语言理解使用的模型不同，并不保证同一句话得到逐字相同的源规格。

模型收到的完整字段合同与最小示例分别提供。仅按输入模式的示例可以没有连线，但连线仍明确使用 `source`、`target` 引用真实节点 ID；空数组不能使字段规范消失。画内标签可以翻译，事实依据必须保留为原输入语言的连续原文引用。图形角色也独立记录：张量、算子、归约和状态的含义来自设计内容，不能依赖某个英文名字或类型标签才得到合适表达。

Web 与可选语义服务流程对不合规的模型回复最多自动修正一次，保留原始事实与补全策略。字段路径与原文引用要求应进入修正请求，而不是通过删掉有效内容来绕过验证。原文依据错误在 Web 中同样归为可修正的验证错误，不误报成运行环境故障。当前 Web Worker 跨边界传递错误文本；本机流程还能携带结构化问题列表，两者的诊断详细程度并不完全相同。宿主 Agent 直接使用 MCP 编译工具时，由宿主处理工具错误。

这里有三个独立的问题。源规格回答设计是什么；用途回答读者这次要理解什么；表现形式决定怎样传达。工程图的实际端点、算法图的运算依赖、状态图的条件、时序图的共同时间轴、商业渲染的主体与空间组织，不能用同一套方框排版替代。它们共享源事实和阅读目标，采用不同的合适表达。

## 设计依据怎样进入产品

以下是对公开设计资料的应用解释，不是来源对 Silicon Canvas 效果的认证。

| 依据 | 在产品中的决定 | 必须验证的结果 |
| --- | --- | --- |
| IBM 要求视觉模型服务于问题、读者和使用环境，并用结构与层级传达重点。 | 先决定阅读任务和可见范围，再安排对象与关系；配色在之后参与表达。 | 同一源设计用于整体介绍、机制解释或局部评审时，范围与阅读方式应有实质区别。 |
| IBM 的技术图规范允许按用途选择节点、连接和路线。 | 直线、正交线和返回通道是表达手段；清楚表达关系优先于统一路线外观。 | 畅通的相对端口不应无故绕行；真实障碍、分支、条件和返回不能为了减少拐弯而被删除。 |
| NN/g 用分组、距离、大小和对比建立阅读层级，并要求在内容中检验层级是否成立。 | 真实归属、主次关系和阅读顺序共同决定构图；提高饱和度或换颜色无法补救错误分组。 | 缩小到使用尺寸后，读者仍能找到入口、重点和结果，准确追踪所需关系。 |

## 组织范围，而不是套场景模板

处理新输入时，系统应优先利用源结构中的证据：真实包含关系、独立输入、分支汇合、循环、共享服务、明确的重复实例以及给定条件。名字里出现 GPU、SoC 或 FIFO 不能成为选择某张已知样图排版的理由。

主图的简化必须有可核对的范围。完整源规格保留所有事实；画面中可见对象、可见关系及本图未展开的源关系分别记录。把若干资源概括成子系统，只适用于读者要理解子系统组织的情况；对于机制图，折叠后仍应能追踪读者关心的实际路径。一个大容器里列出成员名字，不等于已经解释内部工作过程。

同样，重复展开必须由实例和内部结构支持，不能从相似名称推导硬件等价。解释性渲染中的功能分区可以帮助阅读，但不能自动代表实测面积、实体裸片或物理 floorplan。

渲染也分两层组织，而不是把所有对象换成同一种金属芯片。`render_strategy` 先以原始主体、源器件与归属确定尺度：封装、板卡、服务器、机柜或多设备系统。`RENDER3` 再结合阅读任务选择解释范围和拍摄语言，使完整外观、内部功能说明与装配关系采用不同的镜头、层级与标注。多个推理节点应保持独立系统对象，逻辑模块不因外观需要而成为真实 die；局部剖切和拆解也需要对应的输入依据。具体合同见 [渲染策略](render-strategy.md)。

渲染的连线也保留所选关系的含义。选择展示的数据、控制、反馈与时钟关系按源方向表达，相反方向的传递保持可区分；一般接口关联可以采用无箭头细线。整体范围可以稀疏，但不能把已选定的数据传递改成无方向的装饰。没有选定连线的产品主视觉则保持安静，无需凭空增加箭头。

## 在两个入口中使用同一份画面安排

每个编译视图的 `figure_strategy` 概括实际选择的用途、表现形式、阅读方式、可见范围和规划限制。它由本次编译结果派生，不能由已有文件中的缓存声明覆盖，也不是新的技术事实来源。顶层同名字段指向编译时选定视图的策略；每个视图自己的记录与提示词一起保存。

MCP 在编译结果与单图资源中返回这份安排，Web 的完整结果和导出包也保留相同记录。当前网页结果区聚焦提示词和下载，不再单独展示这张策略说明卡；用户或 Agent 可通过绘图包核对采用了什么表达、哪些源内容留在附图或元数据中。

范围统计区分顶层对象与内部对象的展示次数。同一硬件的解释性展开会增加画面中的出现次数，不能据此声称实际硬件数量增加。实际成图的文档尺寸也保持独立的未检查状态；底稿在给定宽度下能容纳文字，只说明底稿的排版情况。

这份策略不声称已经理解所有自然语言，也不提供审美得分。已有的技术补全说明继续单独追踪事实来源；实际图片在审查前仍是 `not_reviewed`。

## 修改图时保留什么

网页生成结果后的“再调整一下”是自然反馈入口，沿用当前结果已保存的设置；“保留当前模块与连接”默认开启，按既有结构锁合同保留源事实与已保存的表现设置。需要改动技术内容时，应明确说明并按需要解除结构锁；不要把仍受锁定的请求描述成已改变事实。

主输入生成与反馈调整是两种不同操作。修改“自定义”中的形式、用途、画幅或配色，用于下一次主输入生成，不立即改动当前结果；页面没有本地套用设置按钮。新的主输入请求重新整理内容，不承诺复用上一版源事实。需要精确保留源规格并改变表现时，Agent 可显式复用该规格和所需设置进行编译。

网页可导出绘图包、提示词文本和项目 JSON，当前没有项目或规格导入界面。保存文件中的完整源事实和设置可交给 Agent 继续工作；API Key 不进入这些文件。兼容既有源规格与历史显式语言设置是共享核心的能力，不应被文档写成一个不存在的 Web 恢复操作。

## 怎样判断系统真的进步

验证分为相互独立的层次，分别保留证据：

1. **事实正确。** 给定成员、条件、数量、归属与关系可追溯；建议补全可辨认，源规格不被布局改写。
2. **表达适合任务。** 概览能解释整体组织，机制图能追踪操作与依赖，控制与时序保留各自含义，渲染同时满足画面目标与源事实。
3. **布局可用。** 对象与文字可读，连线不产生假连接；减少交叉、绕行和空洞不能牺牲前两项。
4. **入口一致。** 同一规范源规格与已解析设置在本机核心、Web Worker 与 MCP 中遵循同一编译合同，导出保持策略、提示词与源范围；这不等于不同语义模型会生成相同规格。
5. **实际图像成立。** 原样使用编译提示词与适当参考调用 Image Gen，在最终位图上检查正确性、结构感和使用尺寸。生成参考图、单元测试与预检结果均不能代替这一步。

新的评估输入应覆盖陌生主题、不同复杂度、稀疏与密集关系、部分与完整描述、显式排除、反馈以及不同表现形式。改名、重排输入顺序和改变实例数量用于检查规则是否依赖特定样例。用于调试的样图与未参与调试的验证输入分开记录；不能只在已展示的几张图上认定改进。

软件验证可以证明合同与执行一致。整体阅读效果和审美仍需要实际成图与读者检查，不能把这两种结论合成一个“通过”标签。
